# 项目架构文档

> 本文档记录 fun-terminal 项目的总体架构设计，是理解项目结构与技术选型的核心参考。
> 依据需求文档 `docs/demands/20261106-01-模拟终端网站整体架构设计.md` 编写。

## 1. 项目概述

- **项目名称**：fun-terminal
- **项目定位**：以"模拟终端"为唯一交互入口的个人网站。访客通过类 Linux 命令行方式浏览站内信息（个人介绍、文章博客等）。
- **核心交互**：仿 Linux 终端界面，键入命令浏览信息，兼具趣味性与技术展示价值。
- **技术栈**：Vue 3 + Vite + TypeScript + Pinia

### 终端渲染选型

- **结论**：自研轻量终端渲染，不引入 xterm.js。
- **理由**：本项目"终端"本质是受控文本输入框 + 输出列表，不需要真实终端协议（ANSI 全量解析、PTY）。自研可完全掌控样式与交互（含 oh-my-zsh 风格提示符），且与 Vue 组件体系更契合。
- **预留**：后期若需富文本/复杂着色，再评估引入 xterm.js。

## 5. 命令分类

命令按归属分为两类：**核心命令**（终端与文件系统基础能力）与**插件命令**（内容挂载与扩展能力），二者遵循同一命令契约（见第 6 节）。

| 类别 | 定位 | 示例 | 加载方式 |
| --- | --- | --- | --- |
| 核心命令 | 终端与文件系统基础能力，随核心集成，不依赖任何插件 | `echo`、`history`、`help`、`clear`、`pwd`、`cd`、`ls`、`cat` | 核心启动即加载 |
| 插件命令 | 内容挂载 + 内容专属/扩展命令；插件通过核心接口实现能力 | 博客插件（挂载 `/mnt/blog` + `blog`）、图片插件（挂载 `/mnt/gallery` + `img`）、挂载管理类命令（`mount`/`unmount` 等） | 插件 `install` 时注册 |

> **归属原则（20261110 确认）**：文件系统（VFS、路径、挂载）以及 `pwd`/`cd`/`ls`/`cat` 等常用文件操作命令属于**核心**，不由插件提供；插件负责「把内容挂载到指定目录」以及「该内容专属的浏览/管理命令」，并且只能通过核心提供的接口（`PluginApi` / `CommandContext`）使用文件系统、挂载与输出。

## 6. 插件化命令架构

### 6.1 设计目标

- 命令**即插即用**：新增命令无需改动核心代码，仅需按约定实现并注册。
- 命令实现与终端 UI、解析器、数据层**解耦**。
- 插件通过核心接口获得能力：安装阶段拿 `PluginApi`（注册命令、挂载内容、只读 VFS、数据源），执行阶段拿 `CommandContext`（参数、VFS、挂载、输出）；插件不直接 import Store 或运行时单例。
- 插件既可**在装配阶段挂载内容树**（如把文章目录挂到 `/mnt/blog`），也可**提供挂载管理命令**（如 `mount`/`unmount`）在运行时通过 `ctx.mounts` 操作挂载。
- 为后续"命令包/工具集"按需加载、远程安装预留扩展点（一期不实现远程安装）。

### 6.2 命令契约（Command Interface）

```ts
interface CommandContext {
  args: string[]                              // 解析后的参数
  options: Record<string, string | boolean>   // 选项
  cwd: string                                 // 当前虚拟工作目录
  env: Record<string, string>                 // 虚拟环境变量
  dataSource: DataSource                      // 数据访问抽象
  commands: readonly Command[]                // 已注册命令快照（help 使用）
  history: readonly string[]                  // 会话历史快照（history 使用，M4）
  setCwd(next: string): void                  // 切换会话目录（cd 使用）
  vfs: Vfs                                    // 只读虚拟文件系统
  mounts: MountApi                            // 挂载管理（mount/unmount/list）
  output: OutputBuffer                        // 输出缓冲（向终端写内容）
}

interface Command {
  name: string                                // 命令名，如 'ls'
  description: string                         // 命令说明，供 help 展示
  usage?: string                              // 用法示例
  execute(ctx: CommandContext): Promise<void> | void
}

/** 插件安装时获得的核心能力：插件只能通过这些接口使用核心 */
interface PluginApi {
  registry: CommandRegistry                   // 注册插件命令
  mounts: MountApi                            // 挂载/卸载内容树
  vfs: Vfs                                    // 只读查询虚拟文件系统
  dataSource: DataSource                      // 数据访问抽象
}

interface CommandPlugin {
  id?: string
  commands?: Command[]                        // 插件提供的命令（可空）
  install?(api: PluginApi): void | Promise<void> // 挂载内容、注册命令
}
```

> 20261110（M3）：`vfs` 与 `mounts` 已随核心文件系统落地为**必填**字段。`Vfs` 是只读契约；写入能力收敛在核心内部 `MutableVfs`（`attachNode`/`detachNode`，仅 `MountManager` 使用），命令与插件拿不到，因此无法绕过挂载白名单改树。
>
> 20261110（M4）：`history` 为**必填**快照字段（`readonly string[]`），由 `CommandSessionAccess.getHistory()` 提供、构建器每次执行前拷贝；命令无法通过它改写会话历史。`help` 的清单仍只来自 `commands`，`Command` 接口未扩展任何字段。

### 6.3 注册机制

- 核心命令随终端核心启动即注册，**先于插件**；插件命令通过 `CommandPlugin.install(api)` 中的 `api.registry` 注册。
- 注册表按命令名建立唯一映射；命令名冲突时 `console.warn` 并**保留先注册者**（核心命令天然优先，D-02），插件无法覆盖 `ls`/`cd` 等核心命令。
- 插件 `install` 允许同步或异步，核心按顺序 `await` 完成；单个插件安装失败时记录错误并跳过，不阻断启动与其他插件。
- 挂载由核心执行：插件只提交只读子树，核心 `MountApi` 负责挂载与 `parent` 指针修正；挂载点限 `/mnt/**`，重复目标告警并保留先挂载者。
- 命令执行前 `await runtime.ready`，确保全部插件装载完成；未来引入异步内容源时不会出现「命令先于挂载」的竞态。
- 插件不得直接 import Pinia Store 或运行时单例；节点构造、路径工具、Markdown 渲染等**纯函数**可直接复用核心实现。

### 6.4 命令清单规划

| 命令 | 类别 | 说明 |
| --- | --- | --- |
| `echo` | 核心 | 输出文本（M2） |
| `history` | 核心 | 查看命令历史（M4） |
| `help` | 核心 | 查看帮助信息（中文，从注册表生成清单；M4 两列对齐与参数校验） |
| `clear` | 核心 | 清屏，保留历史（M2） |
| `pwd` | 核心 | 显示当前工作目录（M4） |
| `cd` | 核心 | 切换虚拟目录（基于 VFS，M4） |
| `ls` | 核心 | 列出目录内容（`-a`/`-l`/多路径，M5） |
| `cat` | 核心 | 读取文本文件内容（`-n`/多文件/图片与二进制提示，M5） |
| `blog` | 插件（博客） | 浏览博客文章；插件负责挂载 `/mnt/blog` |
| `img` | 插件（图片） | 展示图片；插件负责挂载 `/mnt/gallery` |
| `mount` / `unmount` | 插件可提供 | 挂载管理命令示例：插件命令通过 `ctx.mounts` 操作挂载；是否作为固定命令由具体插件决定 |

> 20261110 确认：`cat` 归**核心命令**，原「`cat` 归目录插件还是文本插件」的待定项（D-04）作废。

### 6.5 输出模型（M1 已落地）

`src/terminal/context/OutputBuffer.ts` 将输出块定义为五型可判别联合：

```ts
type OutputChunk =
  | { type: 'text'; content: string } // 普通文本
  | { type: 'html'; content: string } // 受控富文本
  | { type: 'system'; content: string } // 系统提示
  | { type: 'error'; content: string } // 错误输出
  | { type: 'command'; cwd: string; input: string } // 命令回显
```

- `command` 只由终端核心写入，记录执行时 `cwd`，保证回显提示符与历史一致；用户输入走插值，不进入 `html`。
- `html` 只接受受控插件生成的 HTML；动态文本必须转义。
- 一个 chunk 是一个块级输出单元，`write()` 不自动补换行；多行内容放在 `content` 的 `\n` 中。
- `src/terminal/context/buffer.ts` 提供 `createOutputBuffer(sink)`，Store 通过 `append/clear/chunks` 适配，命令层不依赖 Pinia。
- 20261109 经 M1 需求 `20261109-01` 审核确认 D-03 落地为上述五型。

## 7. 虚拟文件系统（VFS）与挂载（核心能力）

- VFS、路径语义与挂载管理属于**核心**（M3 已落地），核心命令与插件命令共用同一套文件系统语义；插件不拥有、也不能替换 VFS。
- 节点模型：目录 / 文件；`/` 为根，`/home/guest` 为会话 home，`/mnt` 为挂载根；`VfsNode.parent` 由实现维护。
- 路径一律 POSIX 绝对路径，`.`、`..`、重复斜杠、尾斜杠的规范化收敛在 `src/fs/path.ts`；输入侧的反斜杠在 `path` 层归一化为 `/`（M4 起以 `\` 开头的路径同样按绝对路径解析），VFS 内部与节点名不含 `\`；`~` 不展开，由命令层基于会话 home 解析。
- 一期**只读**：不提供写操作与权限模型。
- 双契约分层（M3 定稿）：只读 `Vfs` 给命令与插件，`MutableVfs` 仅供挂载管理器使用。

```ts
/** 只读契约：CommandContext.vfs / PluginApi.vfs */
interface Vfs {
  readonly root: VfsNode
  resolve(path: string): VfsResolveResult
  exists(path: string): boolean
  readDir(path: string): VfsNode[] | null
  readFile(path: string): string | null
}

/** 核心内部契约：仅 MountManager 使用，不对外暴露 */
interface MutableVfs extends Vfs {
  attachNode(path: string, node: VfsNode): VfsNode | null
  detachNode(path: string): VfsNode | null
}

/** 挂载接口（核心提供，命令与插件共用） */
interface MountApi {
  mount(target: string, tree: VfsNode): MountResult
  unmount(target: string): boolean
  list(): readonly MountPoint[]
}

type MountResult = { ok: true } | { ok: false; reason: MountFailReason }
type MountFailReason =
  | 'invalid-target'  // 不在 /mnt/** 白名单
  | 'parent-missing'  // 目标父目录不存在或不是目录
  | 'invalid-tree'    // 子树不是目录，或该树已在别处挂载
  | 'duplicate'       // 同一目标已挂载
  | 'nested'          // 与已有挂载点构成父子关系（一期禁止嵌套）

interface MountPoint {
  target: string      // 规范化后的挂载目标
  node: VfsNode       // 挂载的子树根节点
}
```

- **挂载点白名单**：仅 `/mnt/**`（至少一级子目录；段非空且不含 `/`，允许中文等 Unicode 名称）；`/`、`/mnt`、`/home/guest` 不可挂载。
- **挂载语义**：`mount` 覆盖目标节点并修正子树 `parent` 指针；`unmount` 恢复原节点（目标原本不存在则移除该目录）。同一目标重复挂载、同一树实例复用、父子嵌套挂载均 `console.warn` 并拒绝，失败原因通过 `MountResult.reason` 交给命令层生成访客可见文案。
- **装配**：`src/fs/index.ts` 的 `createFileSystem({ homeDir })` 生成初始树（`/`、`/home/<user>`、空目录 `/mnt`）并绑定挂载管理器；应用级单例 `fileSystem` 由 `src/commands/index.ts` 注入 `CommandRuntimeDeps`（`vfs`/`mounts`）。测试用 `createFileSystem()` 新建实例，避免挂载表跨用例污染。
- **插件挂载方式**：在 `install(api)` 阶段调用 `api.mounts.mount('/mnt/blog', tree)`（`tree` 由 `src/fs/build.ts` 的 `buildTree` 从普通对象描述生成）；或在插件命令中通过 `ctx.mounts` 动态挂载/卸载（如插件提供的 `mount`/`unmount` 命令）。插件只能提交只读子树，不能直接替换核心节点。
- **一期内容**：`/mnt/blog`（博客插件）、`/mnt/gallery`（图片插件）由插件在装配阶段挂载；`/mnt` 初始为空目录。会话 home（默认 `/home/guest`）在初始树中内置只读示例内容（`README.md`、`notes/welcome.txt`、隐藏的 `.profile`），供核心 `ls` / `cat` 独立演示与人工验收（M5）；示例内容不经过 `DataSource`，也不占用 `/mnt` 的插件挂载空间。
- 一期仅支持站内静态内容的虚拟映射；真实本地目录（File System Access API）与远程源列入后续扩展，`MountApi` 接口不因此变化。

## 8. 博客集成方案

### 8.1 目标

在终端内通过命令浏览文章，如 `blog list` 列出文章、`blog read <id>` 阅读正文。

### 8.2 一期方案：纯前端静态实现

- 文章以 Markdown 文件存放于 `src/data/static/articles/`（或 `public/`），构建时随包发布。
- 使用 `markdown-it` 渲染为富文本（HTML），支持标题层级、代码块等排版。
- 提供两种查看方式：`cat` 纯文本输出原文；博客插件富文本（md 渲染）展示正文。
- 通过 `StaticDataSource` 提供文章列表与正文读取。
- **挂载方式**：博客插件在装配阶段把 `StaticDataSource` 的清单投影为 `/mnt/blog` 挂载树（`/mnt/blog/<id>.md`），与 `blog` 命令同源；`cat` 读到的是同一份正文，不复制内容。

### 8.3 后期扩展：接入后端

通过 `DataSource` 抽象预留，可平滑切换：

| 维度     | 一期（纯前端）           | 后期（后端）       |
| ------ | ------------------ | ------------ |
| 数据来源   | 静态文件               | REST/API     |
| 文章更新   | 重新构建               | 后台/数据库直接更新   |
| 动态能力   | 无                  | 评论、统计、搜索、鉴权  |
| 实现替换点  | `StaticDataSource` | `ApiDataSource` |

**关键结论**：命令层严格依赖 `DataSource` 接口、而非直接触碰静态文件，一期到二期迁移成本最低——仅需新增 `ApiDataSource` 实现并替换注入，命令代码基本无需改动。

### 8.4 后端选型倾向（后续参考，一期不落地）

- 若引入后端，优先轻量方案（Node.js 系框架或 Serverless），与前端技术栈统一。
- 具体选型待一期完成后、明确动态需求时再单独立项评审。

## 9. 状态管理与数据流

- 终端会话状态（当前虚拟目录 `cwd`、命令历史、环境变量、输出块）由 Pinia 的 `terminal.ts` 管理。
- 输出内容采用流式缓冲（`OutputBuffer` / `createOutputBuffer`），支持 `clear` 清屏。
- 命令内部状态（如文章浏览位置）不全局化，保持命令独立性。
- M1 已落地链路：用户输入 → `TerminalInput` → `Terminal` → `terminal` Store → `OutputChunk[]` → `TerminalOutput`；`Store.submit` 暂代执行链路，M2 替换其内部实现。
- M2 起链路：用户输入 → Parser 解析 → Registry 查找 → Executor 构建 `CommandContext`（`cwd`/`env`/`commands`/`vfs`/`mounts`/`dataSource`/`output`）→ Command 执行 → 读写 VFS / DataSource → OutputBuffer 输出 → 终端渲染。
- M3 起链路补充：`CommandRuntimeDeps` 持有应用级 `vfs`/`mounts`（`src/fs/index.ts` 的 `fileSystem` 单例），`CommandSessionAccess` 原样透传给 `CommandContext`；Store 与执行器不感知文件系统细节，命令查询目录/文件统一走 `ctx.vfs`，修改挂载统一走 `ctx.mounts`。
- M4 起链路补充（导航命令）：`history` 读取 `ctx.history`（Store `history` 数组的**快照副本**，由 `CommandSessionAccess.getHistory()` 在每次执行前拷贝），与 ↑/↓ 浏览同源；`pwd` 直接输出 `ctx.cwd`；`cd` 做 `~` 展开 → `path.resolve(cwd, 参数)` → `ctx.vfs.resolve` 校验 → `ctx.setCwd`。提示符 `PromptBar` 与命令回显块都从 `cwd` 派生，因此 `cd` 成功后三处同步，组件零改动。
- M5 起链路补充（文件浏览）：`ls` / `cat` 通过共享 `path-argument.ts` 做 `~` 展开与 `resolve(cwd, 参数)`，再用 `ctx.vfs.resolve` 取节点；`ls` 读取目录 `children` 后过滤/排序/格式化，`cat` 读取文件 `content` 后做分类、200 KB 阈值、末尾换行与可选行号。两者只写 `text` / `error`，不改变会话状态；home 示例内容由 `src/fs/home-content.ts` 在初始树中生成。
- **启动装配**：M3 现状为 `createCommandRuntime({ dataSource, vfs, mounts })`（核心命令先注册，文件系统单例注入）；M6 将扩展为 `createCommandRuntime({ dataSource, vfs, mounts, plugins })`，再逐个 `await plugin.install(api)`（插件在此时挂载内容树并注册命令），全部完成后 `runtime.ready` resolve，命令执行前 `await ready`。
- **挂载与命令的边界**：挂载只改变 VFS 可见内容，不产生输出；输出统一由命令通过 `ctx.output` 写入，避免插件直接操作 Store。
