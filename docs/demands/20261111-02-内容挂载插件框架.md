## 1. 需求背景

M5 之后，终端已经能导航、浏览目录、读取文本：`ls` / `cat` 在核心 VFS 上工作，home 有示例内容可供验收。但**除了 home 里的示例文件，终端看不到任何「由插件提供的内容」**：`/mnt` 永远是空目录，`CommandPlugin.install` 只能注册命令、不能挂载内容，`createCommandRuntime` 的 `plugins` 数组恒为空。换句话说，M2 冻结的「插件化架构」至今没有跑通过一次真实装载，M8 的博客、M9 的图片都没有可落地的入口。

当前代码的真实状态：

| 项 | 现状 | M6 需要改变的部分 |
| --- | --- | --- |
| `src/commands/CommandPlugin.ts` | `commands: Command[]` 必填；`install?(registry)` 同步、只能注册命令；无 `PluginApi` | 新增强制契约 `PluginApi`（registry/mounts/vfs/dataSource）；`install?(api)` 支持同步/异步；`commands` 改可选 |
| `src/commands/index.ts` | 模块级 `plugins` 恒为空；`createCommandRuntime(deps)` 同步返回；`commands` 是创建时快照；无 `ready` | 接受 `plugins`；核心命令同步注册；按序 `await install`；新增 `ready`；`commands` 改为注册表实时视图 |

**为什么现在做 M6**：

- **M3 的挂载能力至今没有真实调用方**：`MountApi` 只有单测，`/mnt` 始终为空。挂载语义、白名单、失败原因码是否好用，只有被真实插件消费一次才能确认；M6 是最便宜的验证窗口。
- **M2 的插件契约不够用**：`install(registry)` 只能注册命令，无法提交内容树；`plugins` 数组为空也意味着「核心优先、插件隔离」这些约定从未被执行过。
- **M8 / M9 唯一的前置**：博客与图片插件都要在 `install(api)` 里把内容树挂到 `/mnt/blog`、`/mnt/gallery`，并依赖 `ready` 门确保「命令执行时内容已就位」。M6 不做，M8 无法开工。
- **运行时挂载能力需要可演示样例**：架构 6.4 已约定 `mount`/`unmount` 由插件通过 `ctx.mounts` 提供、核心不内置；如果没有一个随应用启用的示例插件，M6 的验收只能靠单测，无法人工确认「插件命令真的能在运行时挂载/卸载」。
- **契约变更窗口最小**：当前唯一的插件实现是 `builtinPlugin`（无 `install`），把 `install` 签名改为 `PluginApi` 现在不需要迁移任何第三方插件；M2 文档第 3.6 节已预告「M6 扩展为 `PluginApi`」。
- **失败隔离与就绪语义越早越好**：M8 的 `install` 会 `await dataSource.fetchArticleList()`；若先有异步插件、后有 `ready` 门，必然出现「命令先于挂载」的竞态与返工。

## 2. 需求描述

### 2.1 目标

把「插件挂载内容 + 注册命令」做成核心可复用的装载机制：插件通过核心 `PluginApi` 拿到 `registry` / `mounts` / `vfs` / `dataSource`，在 `install` 中挂载只读内容树并注册自己的命令；核心保证「核心命令优先、插件按序装载、单插件失败隔离、命令执行前插件已就绪」。后续 M8/M9 只需新增插件目录与 `appPlugins` 一行，不改核心。

```
应用启动
  └─ createCommandRuntime({ dataSource, vfs, mounts, plugins })
       ├─ 同步：注册核心命令（echo / help / clear / pwd / cd / history / ls / cat）
       ├─ 创建 PluginApi（registry / mounts / vfs / dataSource）
       └─ ready = 按数组顺序 await 每个插件：
            ├─ await plugin.install(api)   // 挂载内容树、按需注册命令
            ├─ 成功 → registerAll(plugin.commands)
            ├─ 抛错 → console.error 并跳过该插件（不影响其他插件与启动）
            └─ 空插件 → console.warn 并跳过

用户提交命令
  └─ Store → Executor → await runtime.ready → 解析 → 查找 → 构建 ctx → 执行
                                      └─ 保证插件命令已注册、内容已挂载
```

M6 的演示载体是**示例插件 demo**：它在安装阶段把 `/mnt/demo` 挂到 VFS，并注册 `mount` / `unmount` 两条插件命令，让「运行时挂载/卸载」可以被人工在浏览器里逐项验收。

### 2.2 用户可见行为

1. **启动后 `/mnt` 不再为空**：示例插件在装配阶段挂载 `/mnt/demo`；`ls /mnt` 输出 `demo/`，`ls -l /mnt` 输出 `drwxr-xr-x       -  demo/`，`ls -a /mnt` 输出 `.`、`..` 与 `demo/`。
2. **`/mnt/demo` 内容可读**：`ls /mnt/demo` 按中文排序输出 `docs/`、`notes.txt`、`README.md`；`cat /mnt/demo/README.md`、`cat -n /mnt/demo/notes.txt`、`cat /mnt/demo/docs/plugin.md` 均按 M5 已验收的 `cat` 语义输出。
3. **挂载内容与核心命令无缝衔接**：`cd /mnt/demo` 后 `pwd`、`ls`、`cat docs/plugin.md`、提示符路径全部同步；`cd ..` 回到 `/mnt`；卸载后这些路径消失，核心命令只报「目录不存在」，不崩溃、不改变会话历史。
4. **`help` 自动包含插件命令**：清单从 8 条变为 10 条（新增 `mount` / `unmount`），仍按名称升序、两列对齐、页脚不变；`help mount` 显示 `mount - 挂载示例内容（仅 /mnt/demo）` 与 `用法: mount [挂载点]`，`help unmount` 同理。
5. **`mount` 无参数列出现有挂载点**：输出 `已挂载的目录（1）：` 与缩进两格的 `  /mnt/demo`；没有任何挂载点时输出 `当前没有挂载点。`。
6. **`mount <挂载点>` 挂载示例内容**：`/mnt/demo` 已挂载时输出错误 `mount: /mnt/demo 已挂载`；未挂载时重新挂载并输出 `已挂载: /mnt/demo`，随后 `ls /mnt/demo` 恢复内容。
7. **`mount` 的非法目标**：`/mnt/blog` 等 `/mnt` 下其他目录提示 `mount: 示例插件没有该挂载点的内容: /mnt/blog（当前仅提供 /mnt/demo）`；`/home/guest`、`/tmp/x` 等提示 `mount: 挂载点非法: /home/guest（仅支持 /mnt 下的子目录）`；以上都不改变 VFS。
8. **`mount` 的参数校验**：多个挂载点时提示 `mount: 参数过多（一次只能挂载一个目录）`；带选项时提示 `mount: 不支持的选项: -l`。
9. **`unmount <挂载点>` 卸载示例内容**：`unmount /mnt/demo` 输出 `已卸载: /mnt/demo`，随后 `ls /mnt` 无任何输出（`/mnt` 回到空目录）。
10. **`unmount` 的错误**：未挂载时提示 `unmount: /mnt/demo 未挂载`；缺少参数时提示 `unmount: 缺少挂载点（用法: unmount <挂载点>）`；参数过多时提示 `unmount: 参数过多（一次只能卸载一个目录）`；`/mnt/blog` 等非示例挂载点提示 `unmount: 示例插件只管理 /mnt/demo，无法卸载: /mnt/blog`；`/home/guest` 等提示挂载点非法；以上都不改变 VFS。
11. **卸载不会自动纠正 `cwd`**（与 M4/M5 约定一致）：`cd /mnt/demo` 后执行 `unmount /mnt/demo`，命令本身成功，并追加一条系统提示「提示：当前目录位于已卸载的挂载点内，请使用 cd 切换到其他目录。」；此后 `pwd` 仍输出 `/mnt/demo`，`ls` 报 `ls: 无法访问 /mnt/demo: 目录不存在`，`cd ~` 可恢复。
12. **命令执行前等待插件就绪**：即使某个插件 `install` 是异步的，访客提交的第一条命令也不会误报「未找到命令」；就绪等待期间输入按既有串行队列顺序处理。
13. **单插件失败不阻断终端**：某个插件 `install` 抛错时，终端启动正常、核心命令与其他插件不受影响；失败只记录 `console.error`（访客不可见），该插件的命令不会注册。
14. **无噪音、无新增交互**：成功路径不写 `console.*`（挂载管理器的预期告警除外）；不产生未处理 Promise rejection；无新增快捷键、无 UI 控件、无视觉主题变化。
15. **窄屏与刷新**：375px 下 `mount` 列表、`ls -l`、`cat` 长行自动换行、无横向滚动；刷新后 `cwd` 回 home、历史清空，`/mnt/demo` 随插件重新挂载而再次可见。

> **访客不可见但必须成立**：插件只能通过 `PluginApi` 使用核心能力，不 import Pinia Store、`window`、`fetch` 或运行时单例；插件提交的必须是只读子树，写入能力仍只存在于核心 `MutableVfs`；核心命令始终先于插件注册，插件无法覆盖 `ls` / `cd` 等核心命令。

### 2.4 范围边界

**本次包含**：

- `PluginApi` 契约（`registry` / `mounts` / `vfs` / `dataSource`）与 `CommandPlugin` 扩展（`install(api)` 支持同步/异步、`commands` 可选）。
- 插件装载器：按序安装、`install` 先于命令注册、失败隔离、空插件告警、日志标签。
- 运行时装配：`plugins` 参数、核心命令优先、`ready` 就绪信号、`commands` 实时视图。
- 执行器就绪门：执行前 `await runtime.ready`，并兜底 `ready` 异常。
- 示例插件 demo：挂载 `/mnt/demo`（3 个文件 + 1 个子目录），注册 `mount` / `unmount` 命令。
- 运行时挂载/卸载能力（通过 `ctx.mounts`）与 `cwd` 位于已卸载挂载点内的约定行为。
- 共享命令工具 `path-argument.ts` 由 `builtin/` 上移到 `src/commands/`，供插件命令复用（行为不变）。

约束：

- 插件只把 `PluginApi` 作为能力入口；`PluginApi` **不暴露** `output` / Store / 运行时单例，插件安装阶段不产生任何输出。
- 挂载只改变 VFS 可见内容，输出统一由命令通过 `ctx.output` 写入（核心与插件的命令同一套 `text` / `error` / `system` 块）。

- 装载器与运行时对插件的异常一律隔离：单插件失败只影响自身，`ready` 永不 reject，`execute()` 永不 reject。
- 插件不得 import Pinia Store 或运行时单例；路径 / 节点构造等纯函数可复用核心实现（`@/fs/path`、`@/fs/build`、`@/fs/vfs` 的节点构造器）。

### 3.2 插件契约变更（`CommandPlugin.ts`）

**变更前**：

```ts
export interface CommandPlugin {
  id?: string
  commands: Command[]
  install?(registry: CommandRegistry): void
}
```

**变更后**：

```ts
import type { DataSource } from '@/data/DataSource'
import type { MountApi } from '@/fs/mount'
import type { Vfs } from '@/fs/vfs'
import type { Command } from '@/terminal/context/CommandContext'
import type { CommandRegistry } from '@/terminal/registry/CommandRegistry'

/** 插件安装时获得的核心能力：插件只能通过它使用核心 */
export interface PluginApi {
  /** 注册插件命令（与 commands 字段等效，先注册者优先） */
  registry: CommandRegistry
  /** 挂载/卸载只读内容树 */
  mounts: MountApi
  /** 只读查询虚拟文件系统 */
  vfs: Vfs
  /** 数据访问抽象（M7 起为 StaticDataSource） */
  dataSource: DataSource
}

/** 命令插件接口 */
export interface CommandPlugin {
  /** 插件标识（可选），用于装载日志与冲突诊断 */
  id?: string
  /** 插件提供的命令集合（可选；也可在 install 中注册） */
  commands?: Command[]
  /** 安装钩子：挂载内容树、注册命令；允许同步或异步 */
  install?(api: PluginApi): void | Promise<void>
}
```

**装载语义（由装载器保证，单测锁定）**：

| 场景 | 行为 |
| --- | --- |
| 只有 `commands`、无 `install` | 直接注册全部命令；用于「纯命令插件」 |
| 只有 `install`、无 `commands` | 只执行安装逻辑（命令由 `api.registry` 自行注册） |
| 两者都有 | **先** `await install(api)`，**成功后**再注册 `commands` |
| `install` 同步抛错 / Promise reject | `console.error` 记录插件标识与错误，**跳过该插件**（其 `commands` 不注册），继续下一个插件 |
| 既无 `install` 也无 `commands` | `console.warn` 并跳过（视为配置错误） |
| `install` 内先用 `api.registry.register` 注册、随后抛错 | 已注册的命令**不回滚**（一期不引入事务），但 `commands` 字段不会注册；插件应把注册放在安装流程末尾 |
| `install` 需要异步准备（如 M8 读取文章清单） | 允许返回 Promise；装载器按数组顺序**串行 await**，不并发 |
| `id` 缺失 | 日志标签用 `<未命名插件>`；`id` 只用于诊断，不参与冲突判定 |

约束与理由：

- **`commands` 改可选**：M8/M9 的命令可能依赖 `install` 中异步取到的数据；强制 `commands` 会迫使插件把注册写在 `commands` 数组里而无法保证数据就绪。
- **`install` 先于 `commands` 注册**：让「先挂载、后暴露命令」成为默认顺序，避免命令可执行但内容尚未挂载的窗口；对只有 `commands` 的插件没有影响。
- **不提供卸载插件 / 撤销注册**：一期插件在构建期静态装配，注册表无撤销需求；挂载的撤销由 `MountApi.unmount` 负责。

### 3.3 插件装载器（`src/commands/loader.ts`）

把「安装一个插件」的语义收敛到唯一实现，运行时、测试与未来可能的其他宿主共用：

```ts
import type { CommandPlugin, PluginApi } from '@/commands/CommandPlugin'
import type { DataSource } from '@/data/DataSource'
import type { MountApi } from '@/fs/mount'
import type { Vfs } from '@/fs/vfs'
import type { CommandRegistry } from '@/terminal/registry/CommandRegistry'

/** 装载器宿主：注册表 + 三个核心能力 */
export interface PluginApiOptions {
  registry: CommandRegistry
  mounts: MountApi
  vfs: Vfs
  dataSource: DataSource
}

/** 构造 PluginApi（纯组装，不做校验） */
export function createPluginApi(options: PluginApiOptions): PluginApi {
  return {
    registry: options.registry,
    mounts: options.mounts,
    vfs: options.vfs,
    dataSource: options.dataSource,
  }
}

function pluginLabel(plugin: CommandPlugin): string {
  return plugin.id?.trim() || '<未命名插件>'
}

/**
 * 安装单个插件：先 install，成功后注册 commands。
 * 返回值仅用于测试与诊断；任何异常都被隔离，调用方永远不需要 catch。
 */
export async function installPlugin(api: PluginApi, plugin: CommandPlugin): Promise<boolean> {
  const label = pluginLabel(plugin)
  const commands = plugin.commands ?? []

  if (!plugin.install && commands.length === 0) {
    console.warn(`[fun-terminal] 插件未提供命令或安装逻辑，已跳过: ${label}`)
    return false
  }

  try {
    await plugin.install?.(api)
    if (commands.length > 0) api.registry.registerAll([...commands])
    return true
  } catch (error) {
    console.error(`[fun-terminal] 插件安装失败，已跳过: ${label}`, error)
    return false
  }
}

/** 按数组顺序安装插件；永不 reject */
export async function installPlugins(
  api: PluginApi,
  plugins: readonly CommandPlugin[],
): Promise<void> {
  for (const plugin of plugins) {
    await installPlugin(api, plugin)
  }
}
```

实现要点：

- **`plugin.install?.()` 先执行，`registerAll` 在 try 内**：注册阶段若出现异常（理论上不会，注册表只告警）也按「插件失败」处理，避免半个插件生效。
- **`installPlugins` 串行**：后一个插件可能依赖前一个已挂载的内容（如 M8 的 `/mnt/blog` 被其他插件引用），顺序可预期比并发更重要；插件安装是启动一次的开销，不需要并发。
- **不设超时**：`install` 必须自行结束；一期数据在构建期内联，不依赖网络。若未来出现远程数据源，再评估超时与降级（记入风险）。
- **日志前缀统一 `[fun-terminal]`**：与 `mount.ts` / `registry.ts` 的既有告警风格一致，便于开发定位。

### 3.4 运行时装配（`src/commands/index.ts`）

```ts
import type { CommandPlugin } from '@/commands/CommandPlugin'
import { builtinCommands } from '@/commands/builtin'
import { createPluginApi, installPlugins } from '@/commands/loader'
import { demoPlugin } from '@/commands/plugins/demo'
import { dataSource } from '@/data'
import type { DataSource } from '@/data/DataSource'
import { fileSystem } from '@/fs'
import type { MountApi } from '@/fs/mount'
import type { Vfs } from '@/fs/vfs'
import type { Command } from '@/terminal/context/CommandContext'
import {
  createCommandRegistry,
  type CommandRegistry,
} from '@/terminal/registry/CommandRegistry'

/** 运行时依赖：随里程碑扩展 */
export interface CommandRuntimeDeps {
  dataSource: DataSource
  vfs: Vfs
  mounts: MountApi
}

/** 运行时装配选项：在依赖之上追加插件列表 */
export interface CommandRuntimeOptions extends CommandRuntimeDeps {
  /** 按数组顺序安装的插件；缺省为空 */
  plugins?: readonly CommandPlugin[]
}

/** 运行时实例 */
export interface CommandRuntime {
  registry: CommandRegistry
  /** 已注册命令的实时视图（每次访问返回当前注册表内容，help 使用） */
  readonly commands: readonly Command[]
  deps: CommandRuntimeDeps
  /** 插件装载完成信号：按序 await 全部 install 后 resolve，永不 reject */
  readonly ready: Promise<void>
}

/** 创建命令运行时（核心命令 + 插件） */
export function createCommandRuntime(options: CommandRuntimeOptions): CommandRuntime {
  const { dataSource, vfs, mounts, plugins = [] } = options
  const registry = createCommandRegistry()

  // 核心命令同步注册，先于任何插件（D-02）
  registry.registerAll([...builtinCommands])

  const api = createPluginApi({ registry, mounts, vfs, dataSource })
  const ready = installPlugins(api, plugins)

  return {
    registry,
    get commands() {
      return registry.all()
    },
    deps: { dataSource, vfs, mounts },
    ready,
  }
}

/** 当前启用的插件：M6 起为 demo；M8/M9 依次追加 blog / image */
const appPlugins: readonly CommandPlugin[] = [demoPlugin]

/** 应用级单例 */
export const commandRuntime: CommandRuntime = createCommandRuntime({
  dataSource,
  vfs: fileSystem.vfs,
  mounts: fileSystem.mounts,
  plugins: appPlugins,
})
```

关键取舍：

- **`commands` 改为 getter**：M2 的实现是创建时的 `registry.all()` 快照；插件命令在 `install` 后才注册，快照会漏掉它们，`help` 必须看到插件命令。改成每次访问实时取注册表内容，且执行器已保证 `await ready` 后才执行，因此 `help` 拿到的必是完整清单。
- **`ready` 是 Promise，不是状态字段**：Store / 执行器只需 `await`，不需要订阅或轮询；`installPlugins` 内部逐插件隔离，`ready` 没有 reject 路径。
- **核心命令同步注册**：即使插件异步安装，`ls` / `cd` 等核心命令在模块加载后立即可用；`builtinPlugin` 包装失去意义（唯一作用是从 `commands` 数组注册），删除后核心清单只剩 `builtinCommands` 一个来源，避免「两套注册入口」。
- **`appPlugins` 是模块常量**：新增插件只改这一行；测试不依赖该常量，而是自行传入 `plugins`，避免单例副作用。
- **`deps` 保持原结构**：Store 仍通过 `commandRuntime.deps.{dataSource,vfs,mounts}` 取依赖，无需感知插件。

### 3.7 `mount` / `unmount` 命令

两条命令是**插件命令**（`src/commands/plugins/demo/`），核心不内置；它们演示插件命令如何通过 `ctx.mounts` 在运行时操作挂载，并通过 `ctx.output` 输出结果。

#### 3.7.1 `mount [挂载点]`

| 顺序 | 判断 | 行为 |
| --- | --- | --- |
| 1 | `rejectUnknownOptions('mount', ctx.options, [])` 非空 | `error`：`mount: 不支持的选项: -l`，返回 |
| 2 | `args.length === 0` | `text`：列出现有挂载点（见下），返回 |
| 3 | `args.length > 1` | `error`：`mount: 参数过多（一次只能挂载一个目录）`，返回 |
| 4 | `resolvePathArgument('mount', arg, ctx)` 失败（`~user` / HOME 缺失） | 输出该错误，返回 |
| 5 | 解析结果 `!== /mnt/demo` 且不在 `/mnt/` 下 | `error`：`mount: 挂载点非法: <参数原文>（仅支持 /mnt 下的子目录）` |
| 6 | 解析结果 `!== /mnt/demo` 但在 `/mnt/` 下 | `error`：`mount: 示例插件没有该挂载点的内容: <参数原文>（当前仅提供 /mnt/demo）` |
| 7 | `ctx.mounts.list()` 中已有 `/mnt/demo` | `error`：`mount: /mnt/demo 已挂载`（不调用 `mount`，避免无谓告警） |
| 8 | `ctx.mounts.mount('/mnt/demo', createDemoTree())` 返回 `ok` | `text`：`已挂载: /mnt/demo` |
| 9 | 返回其他原因 | `error`：`mount: 挂载失败: /mnt/demo（<原因中文>）` |

实现骨架：

```ts
import { rejectUnknownOptions, resolvePathArgument } from '@/commands/path-argument'
import type { Command, CommandContext } from '@/terminal/context/CommandContext'
import type { MountFailReason } from '@/fs/mount'

import { DEMO_MOUNT_TARGET, createDemoTree } from './tree'

const REASON_TEXT: Record<MountFailReason, string> = {
  'invalid-target': '挂载点非法',
  'parent-missing': '父目录不存在',
  'invalid-tree': '内容树无效',
  duplicate: '目标已挂载',
  nested: '与已有挂载点构成嵌套',
}

function fail(ctx: CommandContext, message: string): void {
  ctx.output.push({ type: 'error', content: message })
}

function isUnderMnt(target: string): boolean {
  return target.startsWith('/mnt/')
}

function formatMountList(ctx: CommandContext): string {
  const points = ctx.mounts.list()
  if (points.length === 0) return '当前没有挂载点。'
  return [
    `已挂载的目录（${points.length}）：`,
    ...points.map(({ target }) => `  ${target}`),
  ].join('\n')
}

export const mountCommand: Command = {
  name: 'mount',
  description: '挂载示例内容（仅 /mnt/demo）',
  usage: 'mount [挂载点]',
  execute(ctx) {
    const optionError = rejectUnknownOptions('mount', ctx.options, [])
    if (optionError) return fail(ctx, optionError)

    if (ctx.args.length === 0) {
      ctx.output.write(formatMountList(ctx))
      return
    }
    if (ctx.args.length > 1) return fail(ctx, 'mount: 参数过多（一次只能挂载一个目录）')

    const argument = ctx.args[0]!
    const resolved = resolvePathArgument('mount', argument, ctx)
    if (!resolved.ok) return fail(ctx, resolved.message)

    if (resolved.target !== DEMO_MOUNT_TARGET) {
      return fail(
        ctx,
        isUnderMnt(resolved.target)
          ? `mount: 示例插件没有该挂载点的内容: ${argument}（当前仅提供 ${DEMO_MOUNT_TARGET}）`
          : `mount: 挂载点非法: ${argument}（仅支持 /mnt 下的子目录）`,
      )
    }

    if (ctx.mounts.list().some((point) => point.target === DEMO_MOUNT_TARGET)) {
      return fail(ctx, `mount: ${DEMO_MOUNT_TARGET} 已挂载`)
    }

    const result = ctx.mounts.mount(DEMO_MOUNT_TARGET, createDemoTree())
    if (result.ok) {
      ctx.output.write(`已挂载: ${DEMO_MOUNT_TARGET}`)
      return
    }
    if (result.reason === 'duplicate') {
      // 防御分支：命令已在上面预检 list()，正常路径不会走到这里
      return fail(ctx, `mount: ${DEMO_MOUNT_TARGET} 已挂载`)
    }
    fail(ctx, `mount: 挂载失败: ${DEMO_MOUNT_TARGET}（${REASON_TEXT[result.reason]}）`)
  },
}
```

#### 3.7.2 `unmount <挂载点>`

| 顺序 | 判断 | 行为 |
| --- | --- | --- |
| 1 | 选项非空 | `error`：`unmount: 不支持的选项: -f`，返回 |
| 2 | 无参数 | `error`：`unmount: 缺少挂载点（用法: unmount <挂载点>）`，返回 |
| 3 | 参数过多 | `error`：`unmount: 参数过多（一次只能卸载一个目录）`，返回 |
| 4 | `resolvePathArgument` 失败 | 输出该错误，返回 |
| 5 | 解析结果 `!== /mnt/demo` 且不在 `/mnt/` 下 | `error`：`unmount: 挂载点非法: <参数原文>（仅支持 /mnt 下的子目录）` |
| 6 | 解析结果 `!== /mnt/demo` 但在 `/mnt/` 下 | `error`：`unmount: 示例插件只管理 /mnt/demo，无法卸载: <参数原文>` |
| 7 | `ctx.mounts.list()` 中没有 `/mnt/demo` | `error`：`unmount: /mnt/demo 未挂载` |
| 8 | `ctx.mounts.unmount('/mnt/demo')` 返回 `true` | `text`：`已卸载: /mnt/demo`；若 `cwd` 位于该路径下（含相等），追加 `system` 提示 |
| 9 | 返回 `false`（理论上不发生） | `error`：`unmount: 卸载失败: /mnt/demo` |

实现骨架：

```ts
import { rejectUnknownOptions, resolvePathArgument } from '@/commands/path-argument'
import type { Command, CommandContext } from '@/terminal/context/CommandContext'

import { DEMO_MOUNT_TARGET } from './tree'

function fail(ctx: CommandContext, message: string): void {
  ctx.output.push({ type: 'error', content: message })
}

function isAtOrUnder(path: string, target: string): boolean {
  return path === target || path.startsWith(`${target}/`)
}

export const unmountCommand: Command = {
  name: 'unmount',
  description: '卸载示例挂载点（仅 /mnt/demo）',
  usage: 'unmount <挂载点>',
  execute(ctx) {
    const optionError = rejectUnknownOptions('unmount', ctx.options, [])
    if (optionError) return fail(ctx, optionError)

    if (ctx.args.length === 0) {
      return fail(ctx, 'unmount: 缺少挂载点（用法: unmount <挂载点>）')
    }
    if (ctx.args.length > 1) {
      return fail(ctx, 'unmount: 参数过多（一次只能卸载一个目录）')
    }

    const argument = ctx.args[0]!
    const resolved = resolvePathArgument('unmount', argument, ctx)
    if (!resolved.ok) return fail(ctx, resolved.message)

    if (resolved.target !== DEMO_MOUNT_TARGET) {
      return fail(
        ctx,
        resolved.target.startsWith('/mnt/')
          ? `unmount: 示例插件只管理 ${DEMO_MOUNT_TARGET}，无法卸载: ${argument}`
          : `unmount: 挂载点非法: ${argument}（仅支持 /mnt 下的子目录）`,
      )
    }

    if (!ctx.mounts.list().some((point) => point.target === DEMO_MOUNT_TARGET)) {
      return fail(ctx, `unmount: ${DEMO_MOUNT_TARGET} 未挂载`)
    }

    if (!ctx.mounts.unmount(DEMO_MOUNT_TARGET)) {
      return fail(ctx, `unmount: 卸载失败: ${DEMO_MOUNT_TARGET}`)
    }

    ctx.output.write(`已卸载: ${DEMO_MOUNT_TARGET}`)
    if (isAtOrUnder(ctx.cwd, DEMO_MOUNT_TARGET)) {
      ctx.output.push({
        type: 'system',
        content: '提示：当前目录位于已卸载的挂载点内，请使用 cd 切换到其他目录。',
      })
    }
  },
}
```

设计说明：

- **只管理 `/mnt/demo`**（Q-02）：`unmount` 若对任意挂载点开放，访客在 M8 之后可以卸载 `/mnt/blog`，导致 `cat /mnt/blog/x.md` 失效；一期把「卸载示例内容」作为演示能力，不提供通用卸载。
- **命令侧与 `MountApi` 的职责分工**：`mount` 命令先判断目标是否 `/mnt/demo`，只为给出更准确的中文文案；白名单、嵌套、重复、恢复语义的最终判定仍由 `MountApi` 负责。插件在 `install` 中直接调用 `api.mounts.mount` 时，`/`、`/home/guest`、`/tmp/x` 等目标由 `MountApi` 拒绝并告警（PLAN M6 验收项），运行时单测覆盖。
- **`mount` / `unmount` 都先查 `list()` 再操作**：重复挂载与未挂载都属于访客可触发的正常错误路径，若直接调用 `MountApi`，其内部 `console.warn` 会让控制台出现预期噪音（验收项要求「控制台无报错」）。命令预检后给出干净文案；`duplicate` / `false` 分支保留为防御。
- **`cwd` 不自动纠正**：与 M4/M5 约定一致（`ls` / `cat` 对已消失路径报「目录不存在」）；只追加 `system` 提示，提示用户 `cd` 离开。`system` 是 M1 已定型的输出块，无需扩展。
- **`~` 与相对路径**：复用共享 `resolvePathArgument`，`cd /mnt` 后 `mount demo` 与 `unmount demo` 均可工作；`mount ~` 会解析到 home 并被判为非法挂载点（文案回显参数原文）。
- **不写 `html`**：两条命令只产生 `text` / `error` / `system`，不引入转义或 XSS 面。

### 3.8 共享命令工具上移（`path-argument.ts`）

- **现状**：`src/commands/builtin/path-argument.ts` 提供 `expandHomeArgument` / `resolvePathArgument` / `rejectUnknownOptions`，被 `cd` / `ls` / `cat` 使用。
- **问题**：M6 的插件命令同样需要选项校验与「参数 → 绝对路径」；从 `plugins/demo` import `builtin/…` 会让插件依赖核心命令目录的实现细节，且后续 M8/M9 会继续复制。
- **方案**：移动到 `src/commands/path-argument.ts`（文件名与内容不变），`builtin/{cd,ls,cat}.ts` 与 `plugins/demo/{mount,unmount}.ts` 统一从 `@/commands/path-argument` 引入；`src/commands/builtin/README.md` 的说明同步。
- **零行为变更**：函数体逐字保留，M5 已验收的 `cd` / `ls` / `cat` 文案与分支不变，既有 269 个用例应全部通过（仅 import 路径变化）。
- **不新增工具函数**：`rejectUnknownOptions` 的「白名单为空」语义已满足 `mount` / `unmount`（拒绝一切选项），无需为插件另写校验。

### 3.9 契约与不变项

- **`CommandContext` 不变**：插件命令与核心命令使用同一份上下文（`args` / `options` / `cwd` / `env` / `vfs` / `mounts` / `output` / `dataSource` / `commands` / `history` / `setCwd`），没有为插件新增字段。
- **`Vfs` / `MountApi` / `MountResult` 不变**：M6 是纯消费者；示例插件只调用 `mount` / `unmount` / `list`，不触碰 `MutableVfs`。
- **`OutputChunk` 不变**：`mount` / `unmount` 使用已有 `text` / `error` / `system` 三型，`TerminalOutput.vue` 已能渲染。
- **注册表不变**：命令冲突策略沿用「`console.warn` + 保留先注册者」；核心先注册，插件无法覆盖。
- **组件 / 主题不变**：插件挂载只改变数据，命令输出复用既有样式；无新增 class。
- **`help` 实现不变**：M4 的 `help` 已从 `ctx.commands` 动态生成；`commands` 改为实时视图后自动包含插件命令。
- **`DataSource` 不变**：`PluginApi.dataSource` 直接透传现有单例，M7 替换为 `StaticDataSource` 时插件 API 不变。
- **不引入依赖**：`buildTree` / `VfsNode` / `MountApi` 均为已有实现；`package.json` 零改动。
