## 1. 需求背景

当前项目 `fun-terminal` 仅为 Vue 3 + Vite + TypeScript + Pinia 的官方脚手架模板，尚未包含任何业务逻辑（`src/App.vue` 仍是默认演示页面，`src/stores/counter.ts` 为示例 Store）。

本项目定位为**个人网站**，采用"模拟终端"作为核心交互形态：访客无需浏览传统图形化网页，而是通过类似 Linux 命令行（CLI）的方式输入命令，浏览站内信息（如个人介绍、文章博客等）。这一交互形式兼具趣味性与技术展示价值。

本需求文档是项目的**首份需求文档**，目标是：明确产品定位与功能范围、设计整体架构、完成关键技术选型（尤其是插件化命令架构与博客集成方案），为后续迭代开发提供基准。

## 2. 需求描述

### 2.1 产品定位

一个以"终端"为唯一交互入口的个人网站。访客打开网页即进入一个仿 Linux 终端界面，通过键入命令浏览信息，获得类似操作真实系统的沉浸式体验。

### 2.2 功能范围

本需求覆盖以下四大功能点，并明确各自的实现阶段与边界：

| 序号 | 功能点         | 目标用户    | 阶段           | 说明                             |
| -- | ----------- | ------- | ------------ | ------------------------------ |
| 1  | 终端交互界面      | 访客      | 一期           | 网站核心入口，所有功能的统一承载               |
| 2  | 常用 Linux 命令 | 访客      | 一期           | 内置命令 + 外置插件命令，覆盖 `ls`、`cat`、`pwd`、`cd`、`echo`、`history` 等 |
| 3  | 插件化命令架构     | 开发者（内部） | 一期打地基        | 命令可插拔、可扩展；暂不向访客开放"安装"能力        |
| 4  | 文章博客集成      | 访客      | 一期纯前端 / 后期后端 | 在终端内浏览文章；支持 md 富文本渲染与纯文本两种查看方式 |

### 2.3 命令分类

命令按实现形态分为两类，二者均遵循统一的插件契约（见 3.3）：

| 类别     | 定位             | 示例                                 | 加载方式         |
| ------ | -------------- | ---------------------------------- | ------------ |
| 内置命令   | 终端基础能力，随核心集成 | `echo`、`history`、`help`、`clear`、`pwd`、`cd` | 核心启动即加载     |
| 外置插件命令 | 独立功能模块，按需挂载   | 目录插件（`ls` 等，支持挂载本地文件夹到 `/mnt`）、文本插件、图片查看插件、博客插件 | 作为独立插件注册 |

> 说明：`pwd`/`cd` 依赖虚拟文件系统（VFS）上下文，可作为内置基础命令；`ls` 因涉及目录挂载与文件列举，划入「目录插件」。具体命令归属在架构文档中进一步细化。

### 2.4 明确的范围边界（Scope Boundary）

- **插件架构仅面向开发者**：一期仅实现"命令插件化"的底层架构与机制，不提供访客可用的"安装/卸载命令"功能。其目的是为后续扩展保留足够的空间，而非一期交付给终端用户的能力。
- **博客一期为纯前端**：文章以静态数据（如 Markdown 文件、JSON）形式随前端打包，不引入后端。但架构上需为后期接入后端预留清晰的数据接口抽象。
- **不做真实系统能力**：所有"命令"均为站内信息的模拟展示，不涉及真实文件系统、进程、网络等系统级操作。
- **本地文件夹挂载（`/mnt`）**：目录插件支持将站点内的静态资源/内容目录映射为虚拟文件系统的 `/mnt` 挂载点，供 `ls`/`cat` 等命令读取。此为站内静态内容的虚拟映射，非浏览器对访客本地磁盘的访问。
- **语言约定**：不做中英双语切换；博客内容、帮助信息等面向访客的文本使用中文，命令名与选项等遵循英文（Linux 惯例）。

## 3. 方案设计

### 3.1 总体架构分层

```
┌─────────────────────────────────────────────┐
│              展示层（View Layer）             │
│   Terminal 组件 / 输出渲染 / 交互捕获          │
└──────────────────────┬──────────────────────┘
                       │
┌──────────────────────▼──────────────────────┐
│          命令执行层（Command Layer）          │
│  Command Registry / Parser / Executor        │
└──────────────────────┬──────────────────────┘
                       │
┌──────────────────────▼──────────────────────┐
│         命令实现层（Plugin Layer）            │
│  builtin 命令 / 业务插件（blog、about 等）     │
└──────────────────────┬──────────────────────┘
                       │
┌──────────────────────▼──────────────────────┐
│          数据层（Data Layer）                 │
│  DataSource 抽象 / 静态数据 / （后期）后端 API │
└─────────────────────────────────────────────┘
```

### 3.2 模块划分

#### 3.2.1 终端交互模块（Terminal UI）

- 职责：渲染终端界面、捕获键盘输入、管理命令历史（上下键）、展示命令输出。
- 关键能力：光标渲染、命令回显、Tab 补全（可选）、清屏（`clear`）。
- 视觉风格：参照 **oh-my-zsh 基础样式**实现——暗色背景、等宽字体、模拟 `zsh` 提示符（如 `用户名@主机名 ~ %` 形式，包含路径段与分支提示符占位）。
- 技术选型：建议**自研轻量终端渲染**，而非直接引入 xterm.js。理由：本项目的"终端"本质是一个受控的文本输入框 + 输出列表，不需要真实终端协议（ANSI 转义全量解析、PTY 等）。自研可完全掌控样式与交互（含 oh-my-zsh 风格提示符），且与 Vue 组件体系更契合。若后期需要富文本/复杂着色，再评估引入 xterm.js 作为补充。

#### 3.2.2 命令解析模块（Parser）

- 职责：将用户输入的原始字符串解析为结构化的命令（命令名 + 参数数组 + 选项）。
- 设计要点：支持引号包裹参数、空格分隔、`--`/`-` 选项解析；错误命令给出友好提示。

#### 3.2.3 命令注册与执行模块（Registry & Executor）

- 职责：维护命令注册表，负责命令的注册、查找、分发与执行。
- 这是插件化架构的**核心**，详见 3.3。

#### 3.2.4 数据访问模块（DataSource）

- 职责：统一封装数据获取，向上层命令提供数据，向下屏蔽数据来源差异。
- 关键抽象：定义 `DataSource` 接口，提供 `fetchArticleList()`、`fetchArticle(id)` 等方法；一期提供 `StaticDataSource` 实现（读取打包内的静态数据），后期可替换为 `ApiDataSource` 实现（对接后端）。

### 3.3 插件化命令架构设计（核心）

#### 3.3.1 设计目标

- 命令可**即插即用**：新增命令无需改动核心代码，仅需按约定实现并注册。
- 命令实现与终端 UI、解析器、数据层**解耦**。
- 为后续"命令包/工具集"的按需加载、远程安装预留扩展点（一期不实现远程安装）。

#### 3.3.2 命令契约（Command Interface）

定义统一的命令接口，所有命令（内置命令与业务插件）均实现该接口：

```ts
interface CommandContext {
  args: string[]            // 解析后的参数
  options: Record<string, string | boolean>  // 选项
  cwd: string               // 当前虚拟工作目录
  env: Record<string, string>  // 虚拟环境变量
  dataSource: DataSource    // 数据访问抽象
  output: OutputBuffer      // 输出缓冲（向终端写内容）
}

interface Command {
  name: string              // 命令名，如 'ls'
  description: string       // 命令说明，供 help 展示
  usage?: string            // 用法示例
  execute(ctx: CommandContext): Promise<void> | void
}

interface CommandPlugin {
  commands: Command[]       // 该插件提供的命令集合
  install?(registry: CommandRegistry): void
}
```

#### 3.3.3 注册机制

- **内置命令**（`echo`、`history`、`help`、`clear`、`pwd`、`cd` 等）作为核心内置命令集，随终端核心启动即加载。
- **外置插件命令**（目录插件、文本插件、图片查看插件、博客插件等）作为独立插件，通过 `CommandPlugin.install()` 注册到全局 `CommandRegistry`。
- 注册表按命令名建立映射，执行时查找并分发；命令名冲突时后注册者覆盖或抛出警告（策略待定）。

#### 3.3.4 虚拟文件系统（VFS）与目录挂载

目录插件基于一套**虚拟文件系统（VFS）** 工作，将站点内的静态资源/内容目录映射为虚拟路径：

- 站点静态内容（如 `public/` 下的内容、博客文章目录）被挂载到虚拟路径 `/mnt` 下，供 `ls`、`cat`、`cd` 等命令统一读写。
- VFS 提供统一的节点模型（目录/文件）与路径解析，命令层只面向 VFS 接口操作，不直接访问真实文件路径。
- 一期仅支持**站内静态内容的虚拟映射**，不涉及访客本地磁盘的读取。

#### 3.3.5 目录结构规划

```
src/
├── terminal/               # 终端 UI 与核心
│   ├── components/         # Terminal 等组件
│   ├── parser/             # 命令解析器
│   ├── registry/           # 命令注册表
│   └── context/            # 命令上下文、输出缓冲
├── commands/               # 命令实现（插件）
│   ├── builtin/            # 内置命令（echo/history/help/clear/pwd/cd/...）
│   └── plugins/            # 外置插件命令
│       ├── filesystem/     # 目录插件（ls 等 + /mnt 挂载）
│       ├── text/           # 文本插件
│       ├── image/          # 图片查看插件
│       └── blog/           # 博客插件
├── fs/                     # 虚拟文件系统（VFS）
│   ├── vfs.ts              # VFS 节点模型与路径解析
│   └── mount.ts            # 挂载点管理（/mnt 等）
├── data/                   # 数据层
│   ├── DataSource.ts       # 数据源接口定义
│   └── static/             # 静态数据源实现 + 静态内容
├── stores/                 # Pinia 状态（终端会话、历史等）
└── ...
```

### 3.4 博客集成方案分析（重点）

#### 3.4.1 目标

在终端内通过命令浏览文章，例如 `blog list` 列出文章、`blog read <id>` 阅读正文。

#### 3.4.2 一期方案：纯前端静态实现

- 文章以 **Markdown 文件**存放于 `src/data/static/articles/`（或 `public/`），构建时随包发布。
- 使用 Markdown 解析库（如 `markdown-it`）将文章渲染为富文本（HTML），支持标题层级、代码块等排版。
- 提供**两种查看方式**：`cat` 以纯文本方式输出文章原文；博客插件以富文本（md 渲染）方式展示正文。
- 通过 `StaticDataSource` 提供文章列表与正文读取。

**优点**：零后端依赖、部署简单、首版即可上线；内容可纳入版本管理。

**局限**：更新文章需重新构建发布；无法支撑评论、搜索、访问统计等动态能力。

#### 3.4.3 后期扩展方案：接入后端

设计上通过 `DataSource` 抽象预留，后期可平滑切换：

| 维度    | 一期（纯前端）            | 后期（后端）          |
| ----- | ------------------ | --------------- |
| 数据来源  | 静态文件               | REST/API        |
| 文章更新  | 重新构建               | 后台/数据库直接更新      |
| 动态能力  | 无                  | 评论、统计、搜索、鉴权     |
| 实现替换点 | `StaticDataSource` | `ApiDataSource` |

**关键结论**：只要命令层严格依赖 `DataSource` 接口、而非直接触碰静态文件，一期到二期的迁移成本即可降到最低——仅需新增一个 `ApiDataSource` 实现并替换注入，命令代码基本无需改动。

#### 3.4.4 后端选型倾向（供后续参考，一期不落地）

- 若后期引入后端，优先考虑轻量方案（如 Node.js 系框架或 Serverless），与前端技术栈统一，降低维护成本。
- 具体选型待一期完成后、明确动态需求（评论/统计等）时再单独立项评审。

### 3.5 状态管理设计

- 终端会话状态（当前虚拟目录 `cwd`、命令历史、环境变量）由 Pinia 管理。
- 输出内容采用流式缓冲（`OutputBuffer`），支持 `clear` 清屏。
- 避免将命令内部状态（如某篇文章的浏览位置）全局化，保持命令独立性。

## 6. 已确认结论

以下为审核阶段已明确的决策，作为架构文档的输入依据：

1. **终端视觉风格**：参照 **oh-my-zsh 基础样式**实现——暗色背景、等宽字体、模拟 `zsh` 提示符。
2. **命令分类**：命令分为**内置命令**（如 `echo`、`history`，随核心集成）与**外置插件命令**（如目录插件、文本插件、图片查看插件、博客插件）。目录插件支持将本地文件夹挂载到 `/mnt` 供 `ls` 等读取。
3. **博客展示形态**：支持 Markdown 渲染，提供**富文本**（md 渲染）与**纯文本**（`cat`）两种查看方式。
4. **语言约定**：不做中英双语切换；博客内容、帮助信息等面向访客的文本使用**中文**，命令名、选项等使用**英文**（遵循 Linux 惯例）。
