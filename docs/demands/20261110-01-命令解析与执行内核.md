## 1. 需求背景

M1 已完成终端外壳：输入捕获、命令回显、历史、`clear` 清屏、会话 Store 与五型输出块均已落地并经人工验收。但当前 `store.submit()` 内部是**临时外壳逻辑**，不经过任何解析、注册或执行：

```ts
// src/stores/terminal.ts（当前实现，M1 遗留）
function submit(raw: string) {
  const command = raw.trim()
  if (!command) return
  recordHistory(command)
  if (command === 'clear') {
    outputBuffer.clear()
    return
  }
  outputBuffer.push({ type: 'command', cwd: cwd.value, input: command })
  outputBuffer.push({ type: 'system', content: siteConfig.messages.commandUnavailable })
}
```

也就是说：无论输入 `ls -la /mnt`、`echo "hello world"` 还是乱码，终端都只回显同一句「命令系统将在下一里程碑接入」。M1 需求文档 3.8 节已明确这是 M2 必须替换的临时点。

为什么现在必须做 M2：

- **M3** 的 VFS 要作为 `ctx.vfs` 注入命令，必须先有「构建上下文」的执行器，否则 VFS 无处挂载。

## 2. 需求描述

### 2.1 目标

把「用户输入」变成「可插拔命令的可靠执行」，完成插件化架构的最小闭环：

```
原始输入 → 解析（命令名/参数/选项）→ 注册表查找 → 构建上下文 → 执行 → 写入输出
                                              └─ 未找到 / 抛异常 → 失败兜底输出，会话不中断
```

本里程碑结束时，终端具备：

1. 一套**可单测、无 UI 依赖**的命令解析规则；
2. 一个**命令名唯一、冲突可见**的注册表；
3. 一个**统一兜底、串行有序**的执行器；
4. 一个**只加插件不碰核心**的装配入口；
5. 三条真实走完「输入 → 解析 → 查找 → 执行 → 输出」的可见路径：`echo`、`help`、`clear`（Q-01 已确认）。

### 2.2 用户可见行为

1. **命令可执行**：输入 `echo hello world` 回车，回显下一行输出 `hello world`。
2. **引号生效**：`echo "hello world"` 与 `echo 'a  b'` 输出保持引号内的空格；`echo "a\"b"` 输出 `a"b`。
3. **选项被解析**：`ls -la /mnt` 不再被当成一整串文本；命令层收到 `args: ['/mnt']`、`options: { '-l': true, '-a': true }`。M2 中 `ls` 尚未实现，因此终端提示未找到命令（见第 3 条）。
4. **未知命令**：输入未注册命令（如 `ls`、`cd /mnt`、`foo`）时输出一行错误色文本 `ls: 未找到命令，输入 help 查看可用命令`，**不报错中断、不产生未处理 Promise rejection**，可继续输入下一条命令。
5. **帮助**：输入 `help` 列出当前注册表中的全部命令（M2 为 `echo`/`help`/`clear`，M4 起随核心命令集扩展）；`help echo` 展示用法与说明。
6. **异常不炸终端**：命令内部抛错时输出 `命令名: 内部错误：<原因>`，会话保持可用（自动化测试覆盖，GUI 无法主动触发，见 5.1 说明）。
7. **`clear` 成为真实命令**：`clear` 与 `echo`/`help` 一样经过解析、查表、执行，由命令调用 `ctx.output.clear()` 完成清屏；执行效果仍是清空输出并保留历史。`clear` 带位置参数或选项时输出错误 `clear: 不接受参数` 且不清屏；`CLEAR` 按未找到命令处理。
8. **原有行为不回归**：空输入/纯空白回车不产生输出与历史；↑/↓ 历史、输入法、光标、自动滚动与 M1 一致。
9. **执行顺序稳定**：即使连续快速提交多条命令，输出顺序仍与提交顺序一致，不与回显错位。

## 3. 方案设计

### 3.1 总体结构与数据流

```
TerminalInput.vue
      │ submit(raw)
      ▼
Terminal.vue ── store.submit(raw)（void 调用，不阻塞输入）
      │
      ▼
stores/terminal.ts
      ├─ trim / 空输入直接返回
      ├─ recordHistory(raw)
      ├─ outputBuffer.push({ type: 'command', cwd, input })   ← 回显
      └─ executor.execute(raw)                                （clear 也走这条链路）
              │
              ▼
      executor/CommandExecutor.ts
              ├─ parser.parse(raw)                     （纯函数，无 IO）
              ├─ registry.get(parsed.name)
              │     └─ 未找到 → error 块：`name: 未找到命令，输入 help 查看可用命令`
              ├─ buildContext(parsed, output)           （args/options/cwd/env/dataSource/commands/setCwd）
              ├─ await command.execute(ctx)
              │     └─ throw / reject → error 块：`name: 内部错误：<原因>`
              └─ 串行队列：上一条执行完才开始下一条
```

分层约束（与架构文档第 4 节一致）：

| 模块 | 职责 | 依赖方向 |
| --- | --- | --- |
| `parser/CommandParser.ts` | 字符串 → `ParsedCommand` | 不依赖任何项目模块 |
| `registry/CommandRegistry.ts` | 名字 → `Command` 映射 | 仅依赖 `Command` 类型 |
| `executor/CommandExecutor.ts` | 编排、兜底、串行 | 依赖 parser/registry/context 类型，不依赖 Store/UI |
| `executor/context.ts` | 把会话状态 + 解析结果组装成 `CommandContext` | 依赖类型与注入的访问器 |
| `commands/index.ts` | 装配 registry + 内置 + 插件 | 依赖上述三者 |
| `stores/terminal.ts` | 会话状态 + 接线 | 依赖 commands 与 executor，**执行器不反向依赖 Store** |

### 3.2 解析器（`src/terminal/parser/CommandParser.ts`）

在既有接口文件内新增实现（接口与 `ParsedCommand` 类型不变）：

```ts
export function createCommandParser(): CommandParser
```

#### 3.2.1 词法规则

| 规则 | 说明 |
| --- | --- |
| 空白 | 空格 / `\t` / 换行均为分隔符，连续空白折叠；输入整体先 `trim` |
| 单引号 `'...'` | 内部字符**原样保留**（不处理转义、不展开），引号本身不进入 token |
| 双引号 `"..."` | 内部仅 `\"` 与 `\\` 视为转义，其余反斜杠原样保留（`"a\nb"` → `a\nb` 两个字符） |
| 引号拼接 | 相邻的引号段与非引号段属于同一 token：`"a"b` → `ab`，`'a'"b"` → `ab` |
| 未闭合引号 | 宽容处理：到输入结尾为止全部作为该 token（不抛错），见 Q-02 |
| 空引号 | `""` / `''` 产生一个空字符串 token（`echo ""` 输出空行） |
| 引号 token 的选项性 | **带引号的 token 一律视为位置参数**，`echo "--name=x"` 输出 `--name=x` |

#### 3.2.2 选项识别规则

token 按从左到右分类，第 1 个 token 恒为命令名（即使以 `-` 开头，也不再对其做选项解析）：

| 形态 | 判定 | 结果 |
| --- | --- | --- |
| `--` | 精确匹配、非引号 | 终止符：其后所有 token 均为位置参数（第二个 `--` 也按位置参数处理） |
| `--name=value` | `--` 开头且含 `=`，`name` 非空 | `options['--name'] = 'value'`（`=` 之后的全部内容为值，可含 `=`） |
| `--name value` | `--` 开头、无 `=` | 下一 token 存在且**不是**「非引号且以 `-` 开头」也不是 `--` 时，作为值；否则 `options['--name'] = true`（引号包裹的 token 可作值） |
| `-abc` | 单个 `-` 且其后全为字母或数字 | 短选项合并：`-a`、`-b`、`-c` 各为 `true` |
| `-x=value`、`-`、`---x`、`-.a` | 其他以 `-` 开头的形态 | 按位置参数处理（不猜测语义，避免 `-1`、`-.5` 之类被误吞） |

- 同一选项重复出现时**后者覆盖前者**（`--name=a --name=b` → `b`；`-a -a` → `true`）。
- 选项键保留前导 `-` / `--` 原样（与 `CommandContext.options` 现有注释一致），命令内部使用 `ctx.options['-a']`。
- 不支持短选项赋值、`--no-xxx` 取反、选项缩写匹配（一期明确不做）。
- 命令名后可能出现任意顺序的选项与位置参数（`ls /mnt -l` 与 `ls -l /mnt` 等价）。

#### 3.2.3 返回值与边界

- `parse('')` / `parse('   ')` → `{ name: '', args: [], options: {} }`（Store 与执行器都会先拦空输入，此分支只为契约自洽）。
- 纯选项输入 `echo` → `{ name: 'echo', args: [], options: {} }`。
- 解析器**不校验**命令是否存在、不读取任何全局状态、不做路径解析（路径归 M3）。
- 解析器不抛异常：所有输入都返回一个 `ParsedCommand`（未闭合引号按 3.2.1 宽容处理）。

#### 3.2.4 算法骨架

```ts
interface RawToken {
  text: string
  /** 是否来自引号包裹（含拼接段落），用于排除选项识别 */
  quoted: boolean
}

function tokenize(input: string): RawToken[] // 单遍扫描，状态机：normal / single / double / escape
function parse(input: string): ParsedCommand  // token 分类：name → options/args
```

单遍扫描，遇到未加引号的空白即收尾当前 token；引号内空白不切分；`\` 仅在双引号内且后接 `"` 或 `\` 时消耗。

### 3.3 注册表（`src/terminal/registry/CommandRegistry.ts`）

```ts
export function createCommandRegistry(): CommandRegistry
```

| 行为 | 规则 |
| --- | --- |
| 存储 | `Map<string, Command>`，保持注册顺序（`Map` 插入序） |
| `register(command)` | 命令名为空串/纯空白/含空白字符 → `console.warn` 并忽略（不抛错，避免单个坏插件阻断启动） |
| 重名 | **告警并保留先注册者**（D-02）：`console.warn('[fun-terminal] 命令名冲突，已保留先注册的实现: ls')`，后注册者丢弃 |
| `registerAll(commands)` | 逐个调用 `register`，顺序执行 |
| `get(name)` | 精确匹配（区分大小写，命令名统一小写），未找到返回 `undefined` |
| `has(name)` | 等价于 `get(name) !== undefined` |
| `all()` | 返回**新数组快照**（按注册顺序）；调用方修改数组不影响注册表 |

D-02 选择「保留先注册 + 告警」的理由：核心命令先注册即天然优先；插件冲突在控制台可见但不破坏启动，访客侧行为确定。`CommandPlugin.install` 由装配层按「先核心、后插件」顺序调用，保证该优先级可预期。

### 3.4 执行器（`src/terminal/executor/CommandExecutor.ts`）

```ts
export interface CommandExecutor {
  /** 解析并执行一条原始命令；返回的 Promise 在该命令（含排队等待）结束后 resolve，永不 reject */
  execute(raw: string): Promise<void>
}

export interface CommandExecutorOptions {
  registry: CommandRegistry
  parser: CommandParser
  output: OutputBuffer
  buildContext(parsed: ParsedCommand, output: OutputBuffer): CommandContext
}

export function createCommandExecutor(options: CommandExecutorOptions): CommandExecutor
```

#### 3.4.1 单次执行步骤

1. `const input = raw.trim()`；为空直接 `return`（不产生任何块）。
2. `const parsed = parser.parse(input)`。
3. `const command = registry.get(parsed.name)`；未找到 → 写入错误块（3.9），`return`。
4. `const ctx = buildContext(parsed, output)`（每次执行新建，不跨命令复用）。
5. `await command.execute(ctx)`，`try/catch` 包裹同步抛错与 Promise reject。
6. catch → 写入错误块（3.9）+ `console.error('[fun-terminal] 命令执行失败', command.name, error)`。

#### 3.4.2 串行队列

```ts
let tail: Promise<void> = Promise.resolve()
function execute(raw: string): Promise<void> {
  const task = tail.then(
    () => runOnce(raw),
    () => runOnce(raw), // 前一条异常也不阻断后续
  )
  tail = task
  return task
}
```

- 目的：连续快速提交时，**输出块顺序与提交顺序一致**，不会出现 `echo one` 的输出跑到 `echo two` 之后。
- `runOnce` 内部已捕获全部异常，因此 `tail` 不会进入 rejected 状态；`execute` 返回的 Promise 只可能以 fulfilled 结束（调用方无需 catch）。
- 队列串行**不阻塞输入**：`Terminal.vue` 提交后立即清空输入并保持聚焦，排队中的命令在后台按序执行。
- 不设超时与取消：命令均为本地纯计算；M10 若引入长任务再评估。

#### 3.4.3 与 UI 的关系

执行器不感知 Store、Vue、DOM。它只持有 `OutputBuffer` 与注册表/上下文工厂，因此可在 Vitest 中直接实例化测试（3.10）。

### 3.5 上下文构建与契约变更（D-01）

#### 3.5.1 新增 `src/terminal/executor/context.ts`

```ts

  /** 读取当前 cwd（每次执行时取值，不缓存） */
  getCwd(): string
  /** 读取会话环境变量（构建时浅拷贝） */
  getEnv(): Readonly<Record<string, string>>
  /** 切换 cwd（cd 使用） */
  setCwd(next: string): void
  /** 已注册命令快照（help 使用） */

}

export function createCommandContextBuilder(
  access: CommandSessionAccess,

```

构建规则：

- `args` / `options` 为解析结果的**浅拷贝**，命令无法通过修改上下文污染解析结果。
- `env` 为浅拷贝，命令无法直接改会话环境变量（本期无写环境变量的命令）。
- `cwd` 在**执行前一刻**读取，保证排队期间切换目录后行为仍正确。
- `commands` 为注册表快照，`help` 直接使用，禁止命令内部 import 注册表。
- `dataSource` 与 `setCwd` 由 `CommandSessionAccess` 注入，命令实现不感知 Store。

#### 3.5.2 `CommandContext` 契约变更

| 字段 | 变更前 | 变更后 | 用途 |
| --- | --- | --- | --- |
| `args` / `options` / `cwd` / `env` / `dataSource` / `output` | 已存在 | 不变 | — |
| `commands` | — | `readonly Command[]`（新增） | `help` 生成清单（M4 正式使用） |

变更影响：当前**没有任何命令实现**，扩展为纯新增字段，不构成真正的破坏性变更；但会改变「命令怎么写」的模板，因此必须在本里程碑冻结（D-01）。

#### 3.5.3 为什么本期不把 `vfs` 放进上下文

`PLAN.md` M2 技术点写的是「`vfs` 在 M2 通过装配参数注入（测试用桩），M3 起接入真实实现」，M3 交付物又写「扩展 `vfs` 字段」。两者结合的最小实现是：M2 加字段 + 写一个永远为空的 VFS 桩，M3 再换真实实现。本需求文档建议**不这么做**（见 Q-06）：

- M2 没有任何命令使用 VFS，桩实现只能被测试用到，等于提前背一份 M3 的代码；
- 若字段可选（`vfs?: Vfs`），M4 起的命令都要写 `if (!ctx.vfs)` 的防御分支，污染所有命令实现；
- 若字段必填，M2 就必须提供一个假 VFS，M3 再整体替换，属于一次性返工；
- M3 需求文档本来就负责 VFS 实现，字段与实现同批落地，评审边界更清晰。

代价是 M2 的执行器装配**预留**了扩展位置（`CommandSessionAccess` 只增字段），M3 只需在该接口上加 `vfs` 并在 builder 里透传，执行器本身不改。

装配顺序（顺序即冲突优先级）：

1. 创建空注册表；
2. `installPlugin(registry, builtinPlugin)`（`src/commands/builtin/index.ts`）；
3. 按 `plugins` 数组顺序安装各插件（M2 为空数组，M5/M6/M8/M9 逐个加入）；

```ts
// 安装函数（放 src/commands/index.ts，供 M5+ 复用）
export function installPlugin(registry: CommandRegistry, plugin: CommandPlugin): void {
  if (plugin.install) plugin.install(registry)
  else registry.registerAll(plugin.commands)
}
```

- `CommandPlugin` 的 `id`/`commands` 字段不变；`install` 的入参在 M2 为 `CommandRegistry`，M6 扩展为 `PluginApi`（含 mounts/vfs/dataSource），`installPlugin` 调用方式随之调整。
- 插件列表集中在一个 `plugins: CommandPlugin[]` 常量中，新增插件只改数组，**不修改终端核心**——这是本里程碑要证明的扩展点。
- 装配失败策略：单个插件 `install` 抛错时 `console.error` 并继续安装后续插件（不阻断启动）；M2 用单测覆盖。

### 3.7 Store 接入（`src/stores/terminal.ts`）

#### 3.7.1 变更后的 `submit`

```ts

  const command = raw.trim()
```

- 回显块（`command`）仍由 Store 在执行前写入，保证「先看到命令行，再看到输出」。
- 移除 `siteConfig.messages.commandUnavailable` 的写入（该字段在 `site.ts` 中一并删除，避免死配置）。

#### 3.7.2 Store 内的接线

```ts
import { commandRuntime } from '@/commands'
import { dataSource } from '@/data'
import { createCommandContextBuilder } from '@/terminal/executor/context'
```

### 3.9 首批核心命令（`echo` / `help` / `clear`）

Q-01 已确认：M2 提供 `echo`、`help`、`clear` 三个**真实核心命令**。它们既是链路验证，也是后续核心命令集的第一批成员（M4 补充 `pwd`/`cd`/`history`，M5 补充 `ls`/`cat`）。

| 文件 | 命令 | 行为 | 说明 |
| --- | --- | --- | --- |
| `src/commands/builtin/echo.ts` | `echo` | 输出 `ctx.args.join(' ')`；无参数输出空行（`text` 块，空字符串） | 不处理 `-n`/`-e`（一期不做） |
| `src/commands/builtin/help.ts` | `help` | 无参数：按名字升序列出 `name + description`（多列对齐留到 M4）；带参数：展示该命令的 `usage`（缺省用 `name`）与 `description`；未找到：`help: 未找到命令: xxx` | 数据**只**来自 `ctx.commands`，禁止硬编码清单 |
| `src/commands/builtin/clear.ts` | `clear` | 无位置参数、无选项：调用 `ctx.output.clear()`；否则输出 `clear: 不接受参数` 且不清屏 | 接管 M1 的 Store 字符串特例，行为对访客保持一致 |

三者都带 `description`（中文）与 `usage`，供 `help` 展示：

```ts
export const echoCommand: Command = {
  name: 'echo',
  description: '输出传入的文本',
  usage: 'echo <文本...>',
  execute(ctx) { ctx.output.write(ctx.args.join(' ')) },
}
```

`clear` 的实现要点：

- 清屏**只**通过 `ctx.output.clear()`，不 import Store、不操作 DOM；
- 历史由 Store 在提交时记录，命令不清空历史，因此清屏后 ↑ 仍能找回 `clear` 及之前的命令；
- `clear` 现在出现在 `help` 清单中，与 M1「能用但未列出」的过渡状态消除。

> 三个命令都是正式核心命令，文件头不再标注「临时」；M4 及后续里程碑只做增量（`pwd`/`cd`/`history`），不重写它们。

### 3.10 错误与兜底文案

统一遵循 PLAN 第 6 节约定：`命令名: 中文描述`，命令名与选项保持英文。

| 场景 | 输出块 | 文案 |
| --- | --- | --- |
| 未知命令 | `error` | `${name}: 未找到命令，输入 help 查看可用命令` |
| 命令抛错（Error） | `error` | `${name}: 内部错误：${error.message}` |
| 命令抛错（非 Error） | `error` | `${name}: 内部错误：${String(error)}` |
| 空/空白输入 | 无输出 | — |
| `help` 未找到 | `error` | `help: 未找到命令: ${name}` |
| `clear` 带参数/选项 | `error` | `clear: 不接受参数` |

- 错误文案常量集中放在 `src/terminal/executor/messages.ts`（`formatUnknownCommand` / `formatInternalError`），供实现与测试共用，避免测试重复硬编码；M4 起命令自身的错误文案由各命令负责。
- 未找到提示中的「输入 help 查看可用命令」依赖 M2 的 `help` 核心命令（与 `echo`/`clear` 同批落地，Q-01 已确认）。
- 异常路径额外 `console.error`，便于开发定位；错误块本身对访客只展示原因，不暴露堆栈。
