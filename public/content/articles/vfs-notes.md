# 在浏览器里造一个文件系统

这个站点的内容不是一堆页面，而是一棵可以被 `ls`、`cat`、`cd` 遍历的目录树。为了让命令层不关心内容从哪里来，我写了一个只读的虚拟文件系统（VFS）。

## 为什么需要 VFS

如果每条命令都直接去读静态文件，路径语义、错误提示和挂载逻辑会散落在各个命令里。把它们收敛到一层之后：

1. 命令只面向「路径」和「节点」，不关心数据来源；
2. 路径规范化、目录查询只有一份实现；
3. 内容插件只需要提交一棵子树，就能出现在 `/mnt` 下；
4. 未来接后端时，替换数据源即可，命令不用改。

## 核心接口

VFS 对命令只暴露只读能力，写入能力留在核心内部，只给挂载管理器使用：

```ts
interface Vfs {
  readonly root: VfsNode
  // resolve 返回节点与规范化后的绝对路径；readDir 只返回直接子节点；readFile 仅对文件返回正文，目录与不存在的路径都返回 null，命令层因此不需要关心内容来自静态文件还是插件挂载
  resolve(path: string): { node: VfsNode | null; path: string }
  exists(path: string): boolean
  readDir(path: string): VfsNode[] | null
  readFile(path: string): string | null
}
```

> 只读不是妥协，而是一期最合适的能力边界：没有写入，就不需要权限模型和持久化设计。

## 挂载

内容插件在安装阶段提交一棵由普通对象描述生成的子树，核心负责挂到 `/mnt/<名字>`，并修正节点的 `parent` 指针。卸载时恢复原节点即可。

这套约定让「内容」和「命令」可以分开演进：内容插件只关心树长什么样，命令只关心怎么读，`ls` 和 `cat` 因此不需要知道博客插件的存在。

## 一点取舍

路径统一使用 POSIX 语义，`.`、`..`、重复斜杠都在 `path` 层规范化；节点名不允许包含路径分隔符。反斜杠会在输入侧被归一化，避免 Windows 用户按习惯输入时出错。

这些都是很小的决定，但每一条都让后面的命令少写一段分支。
